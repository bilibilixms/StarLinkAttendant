## 1. 引言

### 1.1 编写目的

将需求文档中的功能需求转化为可指导开发与维护的技术设计，统一架构风格、数据规范与接口约定，并为二次开发（如库存管理、包时费率）预留扩展点。

### 1.2 设计原则

| 原则 | 落地方式 |
| :--- | :--- |
| 业务高内聚 | 按业务域拆 Maven 模块，会员/上机/商品/收银/报表/营销互不混杂 |
| 单体低复杂度 | 模块间同 JVM 内 Bean 调用，不引入微服务/RPC，契合单店 Demo |
| 统一基座 | `starlink-common` 提供统一响应、异常、枚举、基类；`starlink-system` 提供认证/RBAC |
| 数据可追溯 | 软删除 + 乐观锁四要素；资金必走流水；关键操作写审计 |
| 前后端分离 | RESTful JSON 接口 + JWT 无状态鉴权；前端独立工程、独立部署 |
| 演示可重建 | DDL 与种子数据脚本化，一条命令重建数据库 |

## 2. 总体设计

### 2.1 系统架构

│  ┌─────────┬─────────┬────────┬─────────┬────────┬───────┐ │

### 2.3 部署拓扑（演示环境）

单台 Windows 开发机本地部署：前端 `npm run dev`（5173）→ 后端 `spring-boot:run`（8080）→ 本地 MySQL80 服务（3306）。前端通过 `.env` 中 `VITE_API_BASE_URL=http://localhost:8080` 直连后端，后端开启 CORS 允许跨域。

## 3. 后端工程设计

### 3.1 模块划分（9 个 Maven 模块）

| 模块 | 包根 | 类型 | 职责 |
| :--- | :--- | :--- | :--- |
| `starlink-common` | `com.starlink.common` | 基座 | `Result<T>`、`PageResult`、`PageQuery`、全局异常、`BaseEntity`、`CommonEnums`、工具类 |
| `starlink-system` | `com.starlink.system` | 基础 | 登录认证、JWT、Spring Security 配置、员工/用户、角色、菜单、权限、审计日志、通知、首页看板 |
| `starlink-module-member` | `com.starlink.member` | 业务 | 会员档案、等级、充值、积分、黑名单 |
| `starlink-module-session` | `com.starlink.session` | 业务 | 区域机位、座位图、会话全生命周期、预约、**按时计费引擎与定时任务** |
| `starlink-module-product` | `com.starlink.product` | 业务 | 商品、分类、套餐 |
| `starlink-module-cashier` | `com.starlink.cashier` | 业务 | 订单、支付、退款、班次、日结 |
| `starlink-module-report` | `com.starlink.report` | 业务 | 经营看板、营收/上机/商品/会员/财务统计、导出 |
| `starlink-module-marketing` | `com.starlink.marketing` | 业务 | 活动、优惠券、充值促销、模拟第三方集成 |
| `starlink-starter` | `com.starlink` | 启动 | 聚合全部模块；启动类、全局配置（CORS/Jackson/MyBatis-Plus）、`application*.yml`、可执行 Jar |

> 计费、库存不单列模块：计费引擎归属 session 模块（费率表 `tariff_plan/tariff_rate`、明细表 `session_timing/billing_record`）；库存仅完成数据层设计（7 张表），出入库管理为后续迭代预留。

### 3.2 模块依赖关系

```
starlink-starter
   ├── starlink-system ──► starlink-common
   ├── starlink-module-member    ──► common（按需依赖 system）
   ├── starlink-module-session   ──► common
   ├── starlink-module-product   ──► common
   ├── starlink-module-cashier   ──► common（跨模块调用会员/商品服务）
   ├── starlink-module-report    ──► common
   └── starlink-module-marketing ──► common
```

- 除 starter 外模块之间**不做 Maven 硬依赖**；跨域协作（如收银扣会员余额）由 starter 同容器装配后以接口 Bean 注入完成。
- 父 POM 统一进行 `dependencyManagement` 锁版本。

### 3.3 分层约定

每个业务模块固定四层包结构：

```
com.starlink.<domain>
├── controller/   // REST 入口，参数校验，返回 Result
├── service/      // 业务接口 + impl/ 实现（事务边界在这一层）
├── mapper/       // MyBatis-Plus BaseMapper，复杂 SQL 放 resources/mapper/*.xml
├── entity/       // 与表一一对应，继承 BaseEntity
└── dto/
    ├── request/  // 入参对象（Create/Update/Query Request）
    └── resp/     // 出参对象（*Response）
```

横切组件位于 `starlink-starter` 的 `com.starlink.config`：`CorsConfig`、`JacksonConfig`（时间格式 `yyyy-MM-dd HH:mm:ss`、时区 Asia/Shanghai、non_null）、`MyBatisPlusConfig`（分页插件等）。

### 3.4 统一技术约定

| 约定 | 说明 |
| :--- | :--- |
| 响应体 | 所有接口返回 `Result<T>`：`code`（0=成功）、`msg/message`、`data`；分页返回 `PageResult<T>`（list + total + pageNum/pageSize） |
| 错误码 | 业务错误以明确 code 返回，如 `10001=登录失败`；未认证返回 HTTP 401 |
| 全局异常 | `@RestControllerAdvice` 捕获参数校验异常、业务异常、兜底异常 |
| 实体基类 | `BaseEntity` 统一定义 `createdAt / updatedAt / deletedAt / version` |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`，MyBatis-Plus `id-type: auto` |
| 逻辑删除 | 字段 `deleted_at`，删除写 `NOW()`，未删为 `NULL` |
| 乐观锁 | `version` 字段，更新带 `WHERE version=?`，防并发覆盖 |
| 时间存储 | `DATETIME(3)` 毫秒精度；Jackson 统一格式化为秒 |
| 金额 | `DECIMAL(10,2)`/`DECIMAL(12,2)`，Java 使用 `BigDecimal`，禁用 double |
| 参数校验 | JSR-303 注解（`@NotNull/@NotBlank/@Min` 等） |

### 3.5 配置设计

| 文件 | 作用 |
| :--- | :--- |
| `application.yml` | 端口 8080、profile=dev、Jackson、文件上传、MyBatis-Plus、本地文件存储、actuator、日志级别 |
| `application-dev.yml` | 数据源（jdbc:mysql://localhost:3306/starlink_attendant）、账号口令、SQL 方言 |

### 4.2 路由与菜单

- 主路由：`/login`（blank 布局）与 `/`（MainLayout，默认重定向 `/dashboard`）。
- 子路由通过 `meta` 声明 `title / icon / group / hidden`，侧边栏据此分组渲染（首页、系统管理、会员管理、上机管理、收银管理、商品销售、经营报表、营销活动、第三方集成）。
- 上机模块独立维护 `modules/session/router.ts`（座位图、会话监控、上机操作、预约管理、换机操作[隐藏]）。
- 全局守卫：未登录访问任意业务页 → `/login`；已登录访问 `/login` → `/dashboard`；同时动态设置页签标题。

### 4.4 状态与请求

| 机制 | 设计 |
| :--- | :--- |
| Pinia stores | `user`（登录态、当前用户、Token 本地持久化）、`permission`（路由/权限码，`hasPermission/hasRoute`）、`app`（界面状态）；各业务模块自带 store |

| 通用能力 | `usePagination`、`useLoading`、`usePermission` hooks；金额、日期、校验工具函数 |

## 5. 数据库设计

### 5.1 设计规范

1. 表名、字段名蛇形小写（`snake_case`），无前缀；Java 侧开启下划线转驼峰。
2. 每表必带 `created_at / updated_at / deleted_at / version`；DDL 对字段给中文 COMMENT。
3. 业务编号唯一约束（如 `uk_session_no`、`uk_computer_no`），高频过滤字段与外键列建普通索引。
4. 字符集 `utf8mb4 / utf8mb4_unicode_ci`，引擎 InnoDB。
5. 资金类列一律 `DECIMAL`，禁止浮点。

### 5.5 关键状态字典

| 实体 | 取值 |
| :--- | :--- |
| 会话 session.status | 0 上机中（进行中）/ 1 临时下机（暂停）/ 2 已下机 / 3 强制下机 / 4 异常中断 |

## 6. 核心业务机制设计

### 6.1 会话状态机

```
            开机 start                 暂停 pause            恢复 resume
 [空闲机位] ─────────► [0 进行中] ◄──────────────► [1 临时下机]
                          │  │                            │（机位=锁定，暂停时长累计）
              下机 end     │  └────管理员 force-end────────┤
                          ▼                               ▼
                     [2 已下机]                      [3 强制下机]
                          │
                    换机 transfer：仅迁移 computer_id，状态与累计费用不变
```

- 开机：校验机位空闲、会员状态正常（散客免会员）→ 创建会话（status=0）→ 机位置 1。
- 暂停：status=1、机位置 2，累计 `pause_count/pause_duration`；恢复后续费计时。
- 下机/强下：写 `end_time`、结算金额、机位回 0；会员余额支付时扣减余额并留痕。

### 6.2 按时计费引擎（系统核心）

费率由 `tariff_plan`（适用范围匹配）+ `tariff_rate`（价格明细）构成：

- `first_minutes`：首时分钟数；`first_price`：首时一口价；`renewal_price`：续费单价（元/分钟）；`daily_cap`：当日封顶价。
- 计费金额：`首时价（前 N 分钟一口价）+ max(0, 计费分钟 - N) × 续费单价`，结果不超过封顶价。
- `SessionBillingScheduler` **每 60 秒**执行：
  1. 扫描全部 status=0 的会话；
  2. 按 start_time/暂停时长重算有效分钟与应收（会员等级折扣计入 `discount_amount`）；
  3. 追加/更新 `session_timing` 分段明细，乐观锁更新 `session` 的 `billed_minutes/total_amount`；
  4. 会员会话按规则扣减余额并记录；
  5. 暂停态（status=1）不产生新增费用。
- 下机时生成 `billing_record`，最终应收以结算时刻重算值为准（定时任务只做预扣/展示）。

### 6.3 预约超时机制

`ReservationTimeoutScheduler` 每 60 秒扫描状态为待确认/已确认且当前时间超过预约开始时间宽限仍未签到（`checked_in_at IS NULL`）的记录 → 状态置 4 超时未到、释放被占机位；签到后将状态置 2 并回写 `session_id` 完成预约转会话。

### 6.4 订单与退款

```
开单(status=0) ──支付pay──► 已支付(1) ──► 已完成(2)
      │                        │
      └──取消cancel──► 已取消(3) └──退款refund──► 已退款(4)
```

- 支付：校验订单与金额；余额支付在同一事务内扣减 `member.balance`；写 `payment_record`。
- 退款：仅已支付订单可退；全额/部分退款写 `refund_record`，余额支付原路退回会员余额，订单状态更新。
- 所有资金动作要求具备审计字段（操作人、时间）。

### 6.5 会员充值事务

`POST /api/member/recharge` 在单事务内：① 校验会员与充值规则；② 更新会员余额（本金 + 赠送额）与成长值；③ 写 `member_recharge`（含支付方式、操作人）；④ 命中充值促销时写积分流水。任一步失败整体回滚。

### 6.6 优惠券生命周期

模板（配置门槛/面额/有效期/总量）→ 发放生成 `coupon`（0 未使用）→ 收银核销（1 已使用，写核销时间/订单）→ 每日 01:00 定时任务把超过 `expire_at` 仍未使用的券置 2 已过期；人工作废置 3。`CampaignServiceImpl` 每分钟按 `start_time/end_time` 自动流转活动状态（发布→生效→结束），下架由人工操作。

### 6.7 交班与日结

- 班次：收银员开班（日班 D / 夜班 N）记录备用金；交班时按班次维度汇总现金/微信/支付宝/余额收款额、退款额，录入实收现金，自动计算长短款，班次关闭。
- 日结：店长选择营业日执行 `generate`，系统聚合当日订单、支付、退款、上机收入、充值等生成 `daily_settlement`；核对后 `confirm` 归档，作为报表数据基准。

## 8. 安全设计

| 维度 | 方案 |
| :--- | :--- |
| 认证 | Spring Security 无状态（`SessionCreationPolicy.STATELESS`）；`JwtAuthenticationFilter` 在用户名密码过滤器前解析 Bearer Token 并构建认证上下文 |
| 登录 | 登录名=手机号；`BCryptPasswordEncoder` 校验密码哈希；成功后由 JWT 工具签发令牌 |
| 授权 | RBAC（employee—employee_role—role—role_permission—permission）；`@EnableMethodSecurity` 支持方法级注解；前端按权限码控制元素 |
| 放行清单 | `/api/auth/**`、`/actuator/**`、`/uploads/**`；其余一律认证 |
| 未认证处理 | 自定义 AuthenticationEntryPoint 返回 401 JSON，前端拦截后跳登录 |
| CSRF/跨域 | 无状态 API 关闭 CSRF；`CorsConfig` 放开前端开发来源 |
| 敏感数据 | 密码 BCrypt；身份证号以 SHA-256 散列存储；传输层生产建议 HTTPS |
| 审计 | 关键业务写 `audit_log`（变更内容以 JSON 快照记录新旧值） |
| 并发与资金 | 乐观锁 version；资金变更事务化且必写流水，保证可对账 |

## 9. 定时任务设计

| 任务类 | 触发 | 职责 |
| :--- | :--- | :--- |
| `SessionBillingScheduler` | fixedRate 60s | 扫描进行中会话，按费率重算费用、写计时明细、更新会话累计与会员余额 |
| `ReservationTimeoutScheduler` | fixedRate 60s | 预约超时未签到自动取消并释放机位 |
| `CampaignServiceImpl` 状态刷新 | fixedRate 60s | 按起止时间自动流转活动状态（生效/结束） |
| `CouponServiceImpl` 过期处理 | cron `0 0 1 * * ?`（每日 01:00） | 到期未使用优惠券批量置为已过期 |

任务依赖 Spring `@EnableScheduling`，单实例运行（与单体部署一致）；任务执行过程输出业务日志便于演示观察。

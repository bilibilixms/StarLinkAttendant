## 1. 引言

### 1.1 编写目的

本文档面向项目评审、开发、测试与演示人员，明确"星络灵侍馆"网吧综合管理系统的业务背景、用户角色、功能需求、非功能需求与验收口径，作为系统设计、开发与验收的统一依据。

### 1.2 项目背景

网吧门店日常运营涉及上机计费、会员储值、商品销售、收银交班、营销活动、经营分析等多条业务线，传统人工记账方式存在计费不准、资金难核对、经营数据不透明等问题。本系统面向**单一网吧门店**，构建一套 B/S 架构的综合管理平台，覆盖"顾客上机 → 自动计费 → 收银结算 → 会员沉淀 → 经营分析"的完整业务闭环。

本项目为**全程脱机的演示项目**：不接入真实支付渠道、短信网关与公安监管平台，相关外部能力均以模拟方式实现，重点验证业务流程与数据模型的完整性。

### 1.3 项目目标

| 目标 | 描述 |
| :--- | :--- |
| 业务闭环 | 打通上机、计费、收银、会员、商品、营销、报表七大业务域，数据互通、全程可追溯 |
| 实时经营 | 提供实时机位状态、进行中会话计费与首页经营看板 |
| 资金一致 | 充值、消费、退款、交班、日结全部留流水，资金数据可对账 |
| 权限可控 | 员工账号基于 RBAC 模型分权，关键操作写审计日志 |
| 易部署演示 | 一套 JDK + MySQL + Node 环境即可本地启动，预置演示账号与种子数据 |

### 1.4 术语定义

| 术语 | 含义 |
| :--- | :--- |
| 会话（Session） | 顾客一次从开机上机到下机结算的完整计费周期 |
| 机位（Computer） | 网吧内一台可上网终端，归属某个区域（普通区/电竞区等） |
| 散客 | 不使用会员身份、以现金等方式直接消费的顾客 |
| 费率方案（Tariff Plan） | 一组计费规则：首时价格、续费分钟单价、封顶价等 |
| 班次（Shift） | 收银员一次上下班之间的收银责任周期，分日班/夜班 |
| 日结 | 营业日结束后对全天营收进行汇总确认的操作 |
| 包时套餐 | 商品/时长组合套餐，区别于按时计费 |

## 2. 总体描述

### 2.1 用户角色

系统预置 5 个员工账号，登录名为手机号，演示密码统一为 `123456`：

| 角色 | 账号示例 | 主要职责 |
| :--- | :--- | :--- |
| 店长 | 13800000001（张伟，E001） | 全部功能：经营看板、日结确认、员工与权限、营销配置、报表 |
| 副店长 | 13800000002（李娜，E002） | 日常运营管理、会员处置、活动配置、报表查看 |
| 收银员 | 13800000003 / 13800000004（王磊等，E003/E004） | 开卡充值、上下机、收银下单、退款、交班 |
| 网管 | 13800000005（刘洋，E005） | 机位维护、换机、强制下机、座位与设备管理 |

会员顾客（系统预置 10 名）通过手机号 + 密码完成身份核验后上机、消费、充值。

### 2.2 运行环境

| 项 | 要求 |
| :--- | :--- |
| 后端运行时 | JDK 17（LTS） |
| 后端框架 | Spring Boot 3.4.x + MyBatis-Plus 3.5.5 |
| 数据库 | MySQL 8.0+，库名 `starlink_attendant`，utf8mb4 / InnoDB |
| 前端运行时 | Node.js 22.18+ |
| 前端框架 | Vue 3.5 + TypeScript + Vite 8 + Element Plus 2.14 + Pinia 3 |
| 浏览器 | Chrome / Edge 最新版本（桌面端 1366×768 及以上分辨率） |
| 外部依赖 | 无；核心业务不依赖互联网，支付/短信/实名认证均为模拟实现 |

### 2.3 总体业务流程

```
会员注册/散客到店
      │
      ▼
选择机位 ──► 预约（可选，超时自动释放）
      │
      ▼
  开机上机 ──► 系统按费率方案每分钟自动计费
      │            │
      │            ├─ 临时下机（锁定机位，暂停计时）
      │            ├─ 换机（会话迁移，计费延续）
      │            └─ 强制下机（管理员干预）
      ▼
  下机结算 ◄── 可使用余额 / 优惠券 / 现金
      │
      ├─ 商品点单（收银台，现金/余额支付，可退款）
      ├─ 会员充值（充赠金额/积分）
      ▼
班次交班 ──► 营业日结 ──► 经营报表与分析
```

### 2.4 设计约束

1. 单店模型，不考虑多门店/连锁数据隔离。
2. 所有支付动作在后端直接标记成功，不调用第三方支付 API。
3. 金额数据库存储为 `DECIMAL(10,2)`（单位：元）。
4. 业务表统一带 `created_at / updated_at / deleted_at / version` 四要素：软删除 + 乐观锁。
5. 业务单号按"前缀 + yyyyMMdd + 序号"生成，保证可读、可按日归集。

## 4. 核心业务流程（验收口径）

1. **会员上机全流程**：会员到店 → 收银员/网管在"上机操作"选择空闲机位并核验会员 → 系统创建会话（进行中）→ 定时任务按分钟累加费用并扣减余额 → 顾客可临时下机（机位锁定）后恢复、或换机继续 → 下机结算，机位释放，会话结束，流水可查。
2. **散客上机全流程**：选择机位与费率方案直接开机 → 下机时按累计时长现金结算。
3. **预约流程**：会员预约机位时段（可选保证金）→ 签到转会话；超过预约时间未签到，定时任务自动取消并释放机位。
4. **商品销售流程**：收银台选商品/套餐开单 → 选择现金或会员余额支付 → 订单完成并写支付流水；需要时发起退款，写退款流水并回退余额。
5. **充值流程**：收银员录入会员与充值金额（匹配充赠规则）→ 事务内余额增加、赠送金额/积分入账、充值流水生成。
6. **交班与日结流程**：收银员开班后其名下收款计入本班 → 交班时系统汇总本班各支付方式收款与退款、登记长短款 → 店长按日生成日结单并确认归档。
7. **营销流程**：店长配置活动/充值促销与优惠券模板 → 向会员发券 → 收银结算时核销优惠券 → 凌晨任务自动过期失效券。

## 5. 非功能需求

### 5.1 性能

| 指标 | 要求 |
| :--- | :--- |
| 核心接口响应 | 列表/详情类接口在演示数据规模下响应 ≤ 1s |
| 计费实时性 | 进行中会话费用刷新周期 ≤ 60 秒 |
| 并发能力（设计目标） | 支持 200 台终端同时在线会话的计费扫描 |
| 前端首屏 | 本地开发环境首屏加载 ≤ 3 秒 |

### 5.2 安全

| 维度 | 要求 |
| :--- | :--- |
| 身份认证 | JWT 无状态令牌；接口默认需登录，登录/静态资源放行 |
| 密码存储 | BCrypt 加盐哈希，禁止明文存储 |
| 权限控制 | RBAC（用户—角色—权限），后端按权限规则拦截、前端按权限控制元素 |
| 资金安全 | 余额变动必须伴随流水表记录；关键业务方法事务化 |
| 操作审计 | 关键业务操作落审计日志，支持事后追溯 |
| 跨域 | 后端开启 CORS，仅允许前端开发来源 |
| 并发控制 | 业务实体带 `version` 乐观锁，避免并发更新覆盖 |

### 5.3 可靠性与可维护性

- 全局异常统一处理，接口返回统一结构 `{ code, msg, data }`（成功 `code=0`）。
- 软删除机制保证历史业务数据不被物理清除。
- 分层架构（Controller—Service—Mapper）+ 按业务域分模块，模块边界清晰。
- 提供数据库结构脚本与种子数据脚本，可一键重建演示环境。

### 5.4 易用性

- 管理端中文界面，Element Plus 组件统一交互。
- 收银相关页面操作步骤短、支持触摸/鼠标双操作。
- 列表页统一提供条件检索、分页、状态标签化展示。
